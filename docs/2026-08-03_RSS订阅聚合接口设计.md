# RSS 订阅聚合接口设计

## 目标

在现有 Koa 后端中增加 RSS 订阅平台管理、主动刷新本地缓存和读取聚合条目的接口。外部 cron 或页面更新按钮只负责调用刷新接口；聚合列表接口始终读取本地 JSON 缓存，不在查询过程中访问外部 RSS。

## 范围

### 本次包含

- 基于 JSON 文件的订阅平台增删改查。
- 后端主动拉取全部平台 RSS。
- 从每个 `<item>` 提取聚合字段并保留原始 item XML。
- 按平台局部更新持久化缓存。
- 从缓存读取全部聚合条目并按发布时间倒序返回。
- 平台级刷新结果、输入校验、超时和并发写入保护。
- 容器运行时数据卷，保证平台配置和缓存不随容器重建丢失。
- 单元测试、服务测试和 HTTP 集成测试。

### 本次不包含

- cron 调度器本身。
- 页面或更新按钮。
- 数据库、Redis 或内存主缓存。
- 聚合列表分页、搜索或平台筛选。
- 用户认证、授权和平台级访问控制。
- 多进程或多实例共享文件时的分布式锁。

## 数据文件

运行数据统一保存在 `backend/data/`：

```text
backend/data/
├── platforms.json
└── rss-cache.json
```

`platforms.json` 保存订阅平台：

```json
[
  {
    "platform": "HDSKY",
    "rss": "https://example.com/hdsky-rss.xml"
  }
]
```

字段约束：

- `platform`：非空字符串，作为不区分大小写的唯一键。
- `rss`：非空且可被 URL 解析，只允许 `http:` 或 `https:` 协议。
- 更新操作只修改 `rss`。修改平台名时先删除旧平台，再创建新平台。

`rss-cache.json` 保存全部平台的聚合条目：

```json
[
  {
    "platform": "HDSKY",
    "title": "示例标题",
    "link": "https://example.com/details.php?id=1",
    "pubDate": "Thu, 26 Mar 2026 16:35:43 +0800",
    "xml": "<item>...</item>"
  }
]
```

其中 `xml` 是 RSS 响应中完整的原始 `<item>...</item>` 字符串。`title`、`link` 或 `pubDate` 缺失时保存空字符串，不丢弃该条目。

两个 JSON 文件都提交初始版本：平台文件使用需求样例中的初始平台，缓存文件初始为 `[]`。所有写入先在同目录生成临时文件，再通过重命名替换目标文件，避免进程中断留下半写入 JSON。

## 技术方案

采用“单一平台文件 + 单一聚合缓存文件”方案：

- 平台配置和缓存结构直观，符合当前轻量 Koa 项目。
- 每个平台刷新成功后只替换该平台的缓存片段。
- 所有平台处理完成后只进行一次缓存文件写入。
- 查询只读取已处理的 JSON，不重复解析 RSS，也不请求外部地址。

新增 XML 解析依赖，用于解析 item 中的 `title`、`link` 和 `pubDate`。解析前从原始 RSS 文本中定位完整 item 块，将匹配到的原文直接写入 `xml`，避免 XML 对象重新序列化改变 CDATA、实体或空白格式。

## 模块职责

保持现有 `route → controller → service` 风格，并增加边界清晰的解析器与文件仓储：

```text
backend/src/
├── routes/
│   └── rss.route.js
├── controllers/
│   └── rss.controller.js
├── services/
│   └── rss.service.js
├── repositories/
│   └── rss.repository.js
└── parsers/
    └── rss.parser.js
```

- `rss.route.js`：声明平台 CRUD、刷新和聚合查询路由。
- `rss.controller.js`：读取路径参数和请求体，调用 Service，并构造统一响应。
- `rss.service.js`：实现平台规则、刷新编排、局部缓存替换、排序和并发控制。
- `rss.repository.js`：读取平台与缓存 JSON，并负责原子写入。
- `rss.parser.js`：从 RSS 文本中提取原始 item XML 和三个业务字段。

应用组装允许注入数据目录和 `fetch` 实现，便于测试使用临时目录和本地 HTTP 服务。生产环境默认使用 `backend/data` 和 Node.js 全局 `fetch`。

## HTTP 接口

所有接口继续使用现有统一响应结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 查询平台列表

```http
GET /rss/platforms
```

成功时 `data` 为 `{ platform, rss }[]`，保持文件中的顺序。

### 新增平台

```http
POST /rss/platforms
Content-Type: application/json

{
  "platform": "HDSKY",
  "rss": "https://example.com/hdsky-rss.xml"
}
```

- 创建成功返回 HTTP `201` 和新平台对象。
- 缺少或非法字段返回 HTTP `400`。
- 平台名不区分大小写重复时返回 HTTP `409`。

### 修改平台 RSS

```http
PUT /rss/platforms/HDSKY
Content-Type: application/json

{
  "rss": "https://example.com/new-hdsky-rss.xml"
}
```

- 成功返回 HTTP `200` 和更新后的平台对象。
- RSS 地址非法返回 HTTP `400`。
- 平台不存在返回 HTTP `404`。
- 修改 RSS 后保留该平台旧缓存，直到下一次刷新成功。

### 删除平台

```http
DELETE /rss/platforms/HDSKY
```

- 成功返回 HTTP `200` 和被删除的平台对象。
- 平台不存在返回 HTTP `404`。
- 删除平台时在同一次受控写操作中删除该平台全部缓存条目。

### 刷新全部缓存

```http
POST /rss/cache/refresh
```

接口读取当前全部平台并并发请求 RSS。每个平台独立处理，单次请求超时为 10 秒。

同一进程中已有刷新任务执行时，新刷新请求直接返回 HTTP `409`，不进入等待队列。

成功响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 2,
    "success": 1,
    "failed": 1,
    "results": [
      {
        "platform": "HDSKY",
        "status": "success",
        "itemCount": 50
      },
      {
        "platform": "HHCLUB",
        "status": "failed",
        "message": "RSS 请求超时"
      }
    ]
  }
}
```

平台级失败属于刷新结果的一部分，因此部分失败或全部平台失败仍返回 HTTP `200`。只有平台文件无法读取、缓存文件损坏、缓存无法写入等服务级故障返回 HTTP `500`。

### 查询聚合条目

```http
GET /rss/items
```

接口仅读取 `rss-cache.json`，不调用外部 RSS。`data` 直接返回全部 `{ platform, title, link, pubDate, xml }[]`：

- 可解析的 `pubDate` 按时间倒序排列。
- `pubDate` 相同的条目保持缓存中的稳定顺序。
- 缺失或无法解析的 `pubDate` 排在列表末尾。
- 不分页，不提供查询筛选参数。

## 刷新数据流

1. 检查刷新状态；已有刷新任务时返回 HTTP `409`，否则标记刷新开始并获取写操作互斥锁，防止刷新与平台 CRUD 交叉覆盖文件。
2. 读取全部平台和当前缓存。
3. 并发拉取各平台 RSS，单个平台执行 10 秒超时和 HTTP 状态检查。
4. 从成功响应中提取每个原始 item XML，并解析 `title`、`link`、`pubDate`。
5. 平台解析成功时，删除缓存中该平台的旧条目并加入新条目；有效 RSS 没有 item 时，该平台缓存变为空。
6. 平台拉取或解析失败时，不修改该平台旧缓存，并记录失败原因。
7. 所有平台完成后，将合并结果原子写入 `rss-cache.json`。
8. 释放互斥锁并清除刷新状态，返回分平台刷新结果。

平台名比较均不区分大小写，但返回值保留 `platforms.json` 中保存的原始大小写。

互斥锁覆盖平台新增、修改、删除和缓存刷新。读接口始终读取上一次完整写入的文件，不读取临时文件。该锁只保证单个 Node.js 进程内的一致性。

## XML 解析规则

- RSS 文本必须是可解析的 XML，并包含 RSS channel 结构；格式错误时整个平台刷新失败。
- 原始 item 块按出现顺序提取，`xml` 保留匹配到的完整文本。
- CDATA 和 XML 实体在提取 `title`、`link`、`pubDate` 时解码为普通字符串。
- 字段值去除首尾空白，字段不存在时使用空字符串。
- item 内部某个业务字段缺失不会导致整个平台失败。
- 原始 RSS 可正常解析但没有 item 时视为成功，并清空该平台旧缓存。

## 错误与并发处理

- 请求体为空、字段类型错误、空字符串或 RSS URL 非法：HTTP `400`。
- 平台不存在：HTTP `404`。
- 平台重名或已有刷新任务执行：HTTP `409`。
- 同一进程中的写操作通过互斥锁串行执行，不允许 CRUD 与刷新发生逻辑竞态。
- 外部 RSS 超时、网络错误、非成功 HTTP 状态或 XML 格式错误：记录为该平台刷新失败，保留旧缓存。
- 平台或缓存 JSON 损坏、权限不足、磁盘写入失败：交给统一异常中间件转换为 HTTP `500`。
- 对外错误消息不包含 RSS 凭据、完整响应内容、堆栈或内部文件路径。

## 容器持久化

现有 Compose 部署增加命名卷，并挂载到容器的 `/app/data`：

```yaml
services:
  backend:
    volumes:
      - rss-data:/app/data

volumes:
  rss-data:
```

Docker 镜像包含初始 `data/` 目录。命名卷首次创建时获得初始平台和空缓存，后续容器重建继续复用该卷。删除命名卷会同时删除运行时平台配置和缓存，此操作不由接口自动执行。

## 测试设计

测试继续使用 Node.js 内置 `node:test` 和 Supertest。

### XML 解析测试

- CDATA 标题和链接被正确解码。
- XML 实体被正确解码。
- `xml` 与输入中的完整原始 item 块一致。
- 字段缺失时返回空字符串。
- 无效日期仍被保留。
- 格式错误的 RSS 抛出可识别异常。
- 有效但无 item 的 RSS 返回空数组。

### 文件仓储测试

- 缺少数据文件时创建合法初始文件。
- 平台和缓存可正常读取、写入并再次读取。
- 写入通过同目录临时文件替换目标文件。
- 损坏 JSON 作为错误上抛，不静默覆盖原数据。

### RSS Service 测试

- 平台名按不区分大小写规则判重。
- 修改和删除不存在的平台返回对应业务错误。
- 删除平台同步删除其缓存。
- 全部平台刷新成功时替换全部对应缓存。
- 部分平台失败时成功平台更新、失败平台保留旧缓存。
- 有效空 RSS 清空该平台缓存。
- 请求超时时只标记对应平台失败。
- 聚合列表按有效 `pubDate` 倒序，无效日期排末尾。
- 重复刷新请求返回 HTTP `409`。
- 并发写操作被互斥控制，不发生丢失更新。

RSS 请求测试使用本地 HTTP 测试服务器，不访问需求样例中的真实地址。

### API 集成测试

- 平台列表、新增、修改和删除成功响应。
- CRUD 的 HTTP `400`、`404`、`409` 响应。
- 刷新接口的成功、部分失败和结果统计结构。
- 聚合接口只读取缓存，返回全部条目且顺序正确。
- 原有健康检查、404 和错误中间件测试继续通过。

## 验收标准

- 平台 CRUD 能持久化到 `backend/data/platforms.json`。
- 刷新接口由后端主动请求全部平台 RSS。
- 每个缓存条目严格包含 `platform`、`title`、`link`、`pubDate`、`xml`。
- 单个平台失败不会阻止其他平台更新，也不会清空失败平台旧缓存。
- 聚合接口不请求外部网络，按 `pubDate` 倒序返回全部缓存。
- 服务重启后平台和缓存仍可读取。
- Compose 容器重建后命名卷中的平台和缓存仍保留。
- 所有新增及原有自动化测试通过。

```bash
cd backend
npm test
npm start
```

```

```

## 风险与边界

- 当前接口没有认证。若服务暴露到不可信网络，任意调用者可修改 RSS 地址或触发服务端请求，需要在部署层限制访问。
- 允许配置任意 HTTP/HTTPS RSS 地址会带来服务端请求伪造风险。本次只做协议校验；公网部署前应增加目标主机白名单或内网地址拦截。
- 单文件缓存适合当前订阅量。平台或 item 数量显著增长后，完整读取和重写 JSON 的成本会上升，届时再评估数据库。
- `xml` 保存完整 item 会使响应和缓存文件较大；本次按需求返回全部数据，不增加分页。
- 进程内互斥锁不支持多个后端实例同时写同一个数据卷。部署时应保持单实例，或后续改用数据库与分布式锁。
