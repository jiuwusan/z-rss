### AI

按推荐的唯一键规则继续，并提出三种缓存实现方案：

1. 单一平台文件 + 单一聚合缓存文件（推荐）：运行数据保存为 `backend/data/platforms.json` 与 `backend/data/rss-cache.json`，刷新时解析成功的平台替换对应条目，最后原子写入缓存文件。结构最简单，符合当前轻量 Koa 项目。
2. 单一平台文件 + 每个平台独立缓存文件：局部更新隔离更直接，但平台删除、命名和聚合读取需要管理更多文件。
3. 内存主缓存 + JSON 快照：查询更快，但需要处理内存与磁盘一致性、启动恢复和并发刷新，当前数据规模下复杂度没有收益。

建议采用方案 1，并在写文件时使用临时文件替换，降低写入中断导致 JSON 损坏的风险。

### AI

已确认采用单一平台文件与单一聚合缓存文件。第一部分设计如下：

- `backend/data/platforms.json` 保存 `{ platform, rss }[]`，初始数据从需求样例迁入；`backend/data/rss-cache.json` 保存 `{ platform, title, link, pubDate, xml }[]`。
- repository 只负责 JSON 文件读取与原子写入；RSS service 负责平台校验、拉取、XML 提取、分平台缓存替换和倒序聚合；controller/route 只处理 HTTP 参数与统一响应。
- 平台接口：`GET /rss/platforms`、`POST /rss/platforms`、`PUT /rss/platforms/:platform`、`DELETE /rss/platforms/:platform`。
- 缓存接口：`POST /rss/cache/refresh` 主动刷新全部平台；`GET /rss/items` 仅读取缓存并按 `pubDate` 倒序返回全部条目。
- `platform` 是不区分大小写的唯一键；更新只允许修改 `rss`；删除平台时同步删除该平台缓存，修改 RSS 地址时保留旧缓存直到下一次成功刷新。

## 第 11 轮

### 用户

确认

### AI

第二部分设计如下：

- 刷新接口读取全部平台并并发拉取 RSS，每个请求设置 10 秒超时，只接受 `http:`/`https:` URL 和成功 HTTP 状态。
- 使用 XML 解析库读取 `title`、`link`、`pubDate`，同时从响应文本截取完整 `<item>...</item>` 保存到 `xml`；缺少字段时使用空字符串，无效 `pubDate` 排在列表末尾。
- 各平台独立处理：成功则整体替换该平台旧缓存；有效 RSS 没有 item 时清空该平台缓存；拉取或解析失败则保留旧缓存。
- 刷新完成后一次性原子写入缓存。响应为 HTTP 200，并返回成功数、失败数和每个平台的结果；只有读取配置、写缓存等服务级故障才返回 500。进程内若已有刷新任务执行，新请求返回 409，避免并发覆盖。
- CRUD 校验：缺少字段或 RSS URL 非法返回 400，平台重名返回 409，修改或删除不存在的平台返回 404。删除平台同步删除对应缓存；任何文件写入都采用临时文件后重命名。
